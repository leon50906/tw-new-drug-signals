# app/ — 訊號板（應用層）

一份每天自動更新的網頁：食藥署〈新成分新藥核准審查報告摘要〉的每一則公告，
展開成許可證號，逐張查明細判定 `07 新藥監視`。

**這一層做的事，根目錄 README 的〈刻意不做〉明文說了它不做。** 三條全部踩到：
它鏡像資料（`data/ledger.json`）、它是批次抓取工具、它把政府主機接進了 CI。
所以它放在 `app/`，與 `reference/`、`docs/` 分開，也不改動那兩層的任何一個字。
`reference/` 仍然是參考實作：這裡 import 它，不改它。

搬出去變成獨立 repo 只需要複製 `app/` 加上 `reference/` 的五個模組。

## 它算得出什麼、算不出什麼

| 訊號 | 這裡有嗎 | 為什麼 |
|---|---|---|
| 新成分新藥核准審查報告摘要 | **有**，完整 | 一頁一頁抓得下來 |
| `07 新藥監視` | **有**，逐張補齊中 | 逐證 API，一次一筆、間隔 30 秒 |
| moiety 首見 | **沒有** | 基線必須是全部 66,440 張證含已註銷的（`M-05`）。本站沒有那份資料，所以不算，也不假裝算得出 |

網頁上的「正規化 moiety」欄位是同一支正規化器跑出來的**字串**，
**不帶任何首見判定**。

## 形狀（依 docs/08）

`data/ledger.json` 是兩層的：

- **每張證一列**：許可證號、真正的發證日、第一次在快照裡看到它的日期、是否已回報。
- **每個訊號一筆證據**掛在那張證底下：哪個訊號、什麼時候確認的、依據是什麼。

證據**只增不改**。同一張證會先以 `07` 進來、幾個月後才被公告確認，那是同一筆的
補強，不是把前一個訊號覆蓋掉——一個 `marker_source` 文字欄位會讓第二個訊號抹掉
第一個，而抹掉之後沒有任何欄位會抗議。回報時間取最早那一筆。

**沒有用尾隨時間窗。** 問的是「這一筆我以前見過嗎」，不是「這一批和上一批差在哪」。
理由：資料本身落後發證日 20–29 天（`M-45`）、41% 的週是零（`M-46`）、
公告中位晚 69 天（`M-14`）——一個七天的窗會安靜地漏掉每一個晚公告的品項。

## 跑

只要標準函式庫。所有指令從 repo 根目錄執行。

```console
$ python3 app/pipeline/fetch_nme_list.py            # 訊號二：21 頁，間隔 3 秒
$ python3 app/pipeline/enrich_details.py --budget 30 # 訊號一：30 張，每張間隔 30 秒
$ python3 app/pipeline/build_site.py                # 產生 site/index.html + data.json
```

`build_site.py` 產生的 `site/index.html` 是**單一自足檔案**：資料直接內嵌，
沒有外部請求，用 `file://` 打開也能看。

### 節流與 422

`enrich_details.py` 一次一筆、預設間隔 30 秒、每輪有預算上限。
主機回 422「連接次數過於頻繁」時，**本輪中止，已完成的部分照樣存檔，
下一輪從斷點續跑**——422 是我方 IP 被限流，不是「這張證不存在」，
也不是「這個標記消失了」。把它記錄成資料會得到一份假的空清單。

第一次跑要補完全部候選證，以 30 秒間隔約需 2.5 小時。
分批跑，或用 `--budget` 讓它跨多輪。

### 控制

`build_site.py` 每次重建都跑一次控制，結果印在網頁上。
**控制沒過就不產生任何輸出**——一個比對器壞掉的頁面比沒有頁面更糟，
它照樣長得像一份清單。

控制成對出現，每個比對器一正一負。負控取自**最容易被誤判為正**的那一族：
`24`／`25` 這兩個名稱同樣含「監視」的碼。只有正控的工具對「抓太多」
完全沒有偵測能力——一個把所有東西都判成 true 的比對器，正控會完美通過。

活體 canary 是 `衛部菌疫輸字第001328號`（IBALIZUMAB）必須帶 `07`。
它有一天不再帶，代表上游語意變了，這份清單的結論就過期了。
canary 只讀 ledger 裡已經查到的那一筆，重建網頁不另外打政府主機。

## 自動化

`.github/workflows/ledger.yml`：每天台北時間 06:00 抓公告 → 補 60 張明細 →
重建網頁 → commit 回 repo → 部署。

更密集沒有意義：上游資料本身落後 20–29 天，公告中位落後 69 天。
一小時跑一次不會更早知道任何事，只會把流量指向政府主機。

## 發布到 Cloudflare Pages

輸出目錄是 `app/site`，裡面已經是成品——**沒有建置步驟**（`index.html` 資料內嵌，
不需要 npm、不需要框架）。`app/site/_headers` 讓 HTML 與 `data.json` 每次回源
驗證：一份被 CDN 快取住的舊清單，讀起來和「今天沒有新藥」一模一樣。

兩條路，**挑一條就好**，兩條都設會部署兩次。

### 路線 A：Git 整合（建議，不用任何 secret）

Cloudflare Dashboard → Workers & Pages → Create → Pages → Connect to Git，
選這個 repo，然後：

| 欄位 | 值 |
|---|---|
| Framework preset | None |
| Build command | *（留空）* |
| Build output directory | `app/site` |
| Production branch | 你要發布的那個分支 |

之後工作流程每天那個 commit 就會自動觸發部署，不必再設定什麼。

### 路線 B：wrangler 直傳（要 secret，但不必把 repo 接給 Cloudflare）

先在 Dashboard 用 **Direct Upload** 建一個 Pages 專案（取個名字，先傳空目錄
或隨便一個檔案佔位），然後在 GitHub repo 設定：

- Secrets：`CLOUDFLARE_API_TOKEN`（權限選 *Cloudflare Pages — Edit*）、
  `CLOUDFLARE_ACCOUNT_ID`
- Variables：`CLOUDFLARE_PROJECT_NAME`（上一步那個專案名）

工作流程裡的部署步驟只有在 `CLOUDFLARE_API_TOKEN` 有值時才會跑，
所以沒設就是路線 A，設了就是路線 B。

### 手動傳一次（不經 CI）

```console
$ npx wrangler pages deploy app/site --project-name=<你的專案名>
```

## 這份清單能講什麼

網頁最上面那三句就是全部：

1. **這張表沒有的，不等於不是新藥。** 公告清單的沉默不可用。
2. **日期是發證日**，優先取 `oriIssueDate`——`issueDate` 會被換發推到後面。
3. **兩個訊號不是同一種東西。** 公告是權威事實；`07` 只是「明細裡有這個碼」。
